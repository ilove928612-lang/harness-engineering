# 基础设施噪声作为 Harness 规格：#59 对 Harness Engineering 架构的启示

> 深度剖析 Anthropic/Gian Segato — [Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise)（2026-02-05）
> 对六大概念、评估方法论、以及 "环境是否算 Harness 一部分" 这一根本问题的架构影响
> 日期：2026-08-14

---

## 一句话重述

#59 用一个干净到令人不安的实验——**同模型、同 harness、同任务集，只改容器资源配额**——把评测报告里最常被忽略的一维直接量化：**6 个百分点的 Terminal-Bench 2.0 摆动，比排行榜前几名之间的差距还大。** 它的真正价值不在数字本身，而在揭示了一个 Harness Engineering 一直在回避的问题：

**Harness 的"规格"，从来不只是 AGENTS.md + linter 规则，还包括它运行的虚拟机长什么样。**

#38（基准错位）喊了"model / harness / 环境折叠进一个分数"，但没人给出环境的定量证据。#59 补上了最后一块。

---

## 实验结构还原

| 维度 | 设置 |
|------|------|
| 基准 | Terminal-Bench 2.0（主） + SWE-bench（交叉验证） |
| 变量 | 容器资源配额，6 档：严格 1x → 2x → 3x → 4x → 5x → 完全不限 |
| 固定项 | 模型、harness、任务集、时限 |
| SWE-bench | 227 题 × 10 次采样，内存 1x→5x |

### 关键数据

```
基础设施错误率：5.8% (1x) → 2.1% (3x, p<0.001) → 0.5% (不限)
1x–3x 区间：成功率在统计噪声内波动（p=0.40）
3x 以上：性质突变 —— 基础设施错误只再降 1.6pp，
        成功率却跳了近 4pp
SWE-bench 交叉验证（1x→5x）：+1.54pp，方向一致但幅度小得多
```

---

## 两个拐点，两类被测量的智能体

数据里藏了两个相变点，比"数字大小"本身重要得多：

### 拐点一：1x → 3x（修可靠性，不改变被测对象）

在这个区间内成功率**统计上无差异**（p=0.40）。#59 的解释很犀利：

> 1x 下崩掉的任务，多半本来就没走在正确路径上——智能体在探索、撞资源墙、被抢占，但它从来就没做出正确决策。多给资源只是让它崩溃得更晚，不是让它做得更对。

这个阶段加资源，修的是 harness 的**可靠性**——让"本来能做出来的"不被基础设施打断。这不是作弊，是**减少噪声**。和 #23（Anthropic 质量回归复盘）里"基础设施抖动导致单次评分失效"的教训同构。

### 拐点二：3x → 不限（改变被测对象本身）

过了 3x 之后，基础设施错误率曲线**几乎走平**（只再降 1.6pp），但成功率却**跳了 4pp**。这不是噪声被压掉，而是**智能体换了一整套策略**：

- 在 3x 配额下能用的策略：标准库手写、精简依赖、轻量测试
- 在不限配额下解锁的策略：装 `pandas` / `networkx` / `scikit-learn` 全家桶、开昂贵子进程、跑吃内存的完整测试套件

文中的活例子 `bn-fit-modify`：有的模型第一步就装全家桶，1x 下装到一半 OOM，连一行解题代码都没写；另一些模型默认用标准库手写数学。**两种都是合法的测量对象，但不声明配额就把它们折叠成一个分数，你根本不知道自己测的是什么。**

## 对 Harness Engineering 架构的五个架构启示

### 启示一：Harness 规格 = 行为约束 + 环境规格，二者缺一不可

回看六大核心概念，#1（仓库即记录系统）说"不在仓库里的东西对智能体不存在"。但一个微妙的事实是：**资源配额从来不在仓库里**——它在 CI runner 配置、Docker 限制、云平台 plan 里。而 #59 证明了这个"仓库外的东西"对分数有 6pp 的影响。

**架构补丁：** Harness 的完整规格必须包含一个 `INFRA.md`（或等价的 machine-readable 声明）：

```yaml
# INFRA.md — harness 环境规格（与 AGENTS.md 同级一等公民）
per_task:
  guaranteed_allocation:
    cpu_cores: 2
    memory_gb: 8
    disk_gb: 20
  hard_kill_threshold:
    memory_gb: 16      # 独立的硬杀阈值，与保底不同
    wall_clock_minutes: 120
  allowed_egress: whitelist
  concurrency_cap: 1
```

这和 #2（地图而非手册）的精神一致——环境规格也应该是一个小入口点，指向更详细的 CI runner 定义。**低于 3pp 的排行榜差距，在 INFRA.md 未公开且未对齐前都该被打问号。**

### 启示二："3x 折中点"作为 harness 设计的启发式

#59 在 Terminal-Bench 2.0 上找到了一个有趣的折中点：**3x 配额下，底与顶的分数落在彼此的统计噪声内**——这是"资源充足到不干扰"的最低代价。

把这个观察翻译成 harness 设计原则：

> **harness 的资源分配应该校准到"最紧档与最松档的分数差在彼此的噪声内"。**

这不是"配大点就行"，而是"配到噪声消失的最低代价"。和 #34 Harness-Bench（固定任务变配置）的实验哲学完全同构——**先找到让基础设施不再成为变量的最小代价，再谈模型对比。**

### 启示三：资源配额是 harness 的"价值观锁定"

#7（harness 是牲畜）说 harness 编码了对模型能力的假设。#59 揭示了一个更深层的锁定：**资源配额编码了对"好代码应该长什么样"的价值观。**

| 配额 | 奖励的编程风格 | 隐含的价值观 |
|------|-------------|-----------|
| 紧（1x） | 精简、标准库优先、显式内存管理 | 效率、克制 |
| 中等（3x） | 适度抽象、常见依赖、合理测试 | 工程平衡 |
| 阔（不限） | 重型工具链、全家桶安装、暴力破解 | 速度、完备 |

和 #24 AHE、#11 Meta-Harness 的讨论合起来，一个完整的图景是：**每一个 harness 都在通过 AGENTS.md（行为）、linter（结构）、INFRA（资源）三根杠杆编码一种"什么样的解决方式才算好"的价值观。** 不声明这三者，排行榜上的差距就无法解读。

### 启示四：基础设施噪声是运行时污染的资源侧，与 #61 的信息侧构成完整诊断

运行时污染有两个正交的侧面：

| 侧面 | 机制 | 量化（#59 vs #61） |
|------|------|-------------------|
| **资源侧** | 配额、并发、带宽、时限、硬件规格 | 6pp（Terminal-Bench 2.0），+1.54pp（SWE-bench） |
| **信息侧** | 答案泄漏、搜索集与评测集重叠 | #61 Cursor 奖励作弊 |

两篇合起来才是"环境这一维"的完整体检。harness 设计时需要**同时**防御两路污染：INFRA.md 管资源侧，评测集隔离（#47 Demystifying evals）管信息侧。

### 启示五：时间维度也是一个基础设施噪声源

#59 作者在正文明确提到但**未正式量化**的其他混杂源：

- 集群健康度
- 硬件规格（不同代际 CPU）
- 出口带宽
- **一天中的时间**（API 时延随流量波动，通过率呈日周期）

最后一条尤其值得注意：如果通过率随一天中的时间波动，那么"harness 运行在哪个时区、哪个时间窗口"也是一个需要声明的实验变量。这指向一个被忽略的架构实践——**harness 运行应该有固定的时间窗口**，或者至少在报告里声明运行时间分布。

## 与既有概念体系的整合

把 #59 的洞见映射回六大概念：

| 六大概念 | #59 的补充 |
|---------|----------|
| #1 仓库即记录系统 | 环境规格（INFRA.md）必须进仓库，否则 6pp 的分数差异不可复现 |
| #2 地图而非手册 | INFRA.md 也应是小入口点，指向 CI runner 详细定义 |
| #3 机械化执行 | 资源配额可以 lint 化——`container_limits.py` 校验声明与运行时一致 |
| #4 智能体可读性 | 智能体需要知道"我能用多少资源"，否则策略选择是盲目的 |
| #5 熵管理 | 基础设施噪声是 harness 熵的一部分，需纳入 GC 循环 |
| #6 Harness 定义 | "Harness"的定义必须包含环境规格，否则定义不完整 |

## 三个未被 #59 回答的开放问题

### 问题一：6pp 是在 Terminal-Bench 2.0 上的上限吗？

SWE-bench 上只有 +1.54pp，方向一致但幅度小得多。**是基准不同，还是任务类型不同？** Terminal-Bench 偏"探索+工具使用"，天然更依赖资源；SWE-bench 偏"精确定位+修改"，资源敏感度低。这意味着 harness 设计时，**任务集选择本身就是一个基础设施噪声放大器**——不能只用一个基准来声明"我们配够了资源"。

### 问题二：3x 折中点在其他基准上成立吗？

Terminal-Bench 2.0 上 3x 是折中点。SWE-bench 上幅度小得多（+1.54pp），**是不是意味着 SWE-bench 的折中点在 2x 甚至更低？** 更一般地，**有没有一个基准无关的"资源充足性测试"方法**——比如 #34 Harness-Bench 的思路，但专门针对资源维度？

### 问题三：紧配额的智能体策略在真实生产中是否更可迁移？

#59 说"紧配额奖励写精简高效代码"，"阔配额奖励重型工具暴力破解"。但 harness 评测的终极问题是**分数能否迁移到真实开发环境**。真实生产中资源约束是什么？如果真实开发环境本身就阔绰（现代工程师的笔记本、云端 IDE），那紧配额 harness 测出来的"效率优势"会不会是**训练有素的人对真实场景的过度约束**？这个问题 #59 没有回答，但它为回答提供了实验框架。

## 一句话结论

**#59 的真正贡献不是"6 个百分点"这个数字，而是它证明了一个此前只是修辞的命题——环境是 harness 规格的一部分，且影响大到可以逆转排行榜。** 对 Harness Engineering 架构来说，这意味着 `INFRA.md` 应该和 `AGENTS.md` 一样成为一等公民，"3x 折中点"应该成为资源校准的启发式，而"低于 3pp 的榜单差距都值得怀疑"应该成为每一条评测报告的默认脚注。
